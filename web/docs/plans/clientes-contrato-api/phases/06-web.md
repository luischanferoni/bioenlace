# Fase 06 — Web

## Objetivo

La web sigue el mismo criterio que los móviles: renderiza lo que manda la API.

## Tareas

- Eliminar el HTML concatenado en los 33 archivos de `frontend/web/js`; usar plantillas y clonado (Camino A).
- Textos de UI literales: vienen de la API o de un único módulo de infraestructura.
- Cliente HTTP único en JS que interpreta el contrato de errores.
- Vistas PHP: mover a page builders la lógica de request, rol y URL (40 casos) según vistas delgadas.
- Eliminar JS y vistas específicas por tipo de episodio que dupliquen lo que ahora llega por metadata.
- Asistente SPA: confirmar que consume `client_open` sin inferir por URL.
- Guardas de CI para HTML en JS y textos literales.

## Criterio de salida

Contadores de web en su nuevo tope. Pruebas de humo de HC, captura y tablero.

## Avance

La verificación del asistente SPA confirma que el cliente distingue las acciones por `client_open.kind`, sin inferir el tipo de pantalla a partir de la URL: para `ui_json` toma `client_open.api.route`; en tarjetas `native` prioriza el path web declarado y conserva un fallback de ruta si falta; en un paso de flow `native` no intenta montar la pantalla web. Los `intent` se envían al endpoint conversacional con `action_id`. Se conserva el fallback de navegación para payloads legacy que no traen `client_open.kind`. La normalización del sobre cubre la preservación de targets `ui_json` y `native` en `common/tests/unit/platform/assistant/AssistantEnvelopeFlowTest.php`.

La verificación del asistente quedó integrada con las migraciones de renderizado y extracción de lógica descritas a continuación. El estado final de esta fase cumple los criterios de vistas delgadas y renderizado DOM; los smoke tests de HC, captura y tablero quedan como validación pendiente no bloqueante.

Se centralizaron en `BioenlaceApiClient` el rótulo de botón, el estado vacío y el error repetidos por los widgets de descarga PDF de laboratorio y receta. El estado vacío que antes se construía como HTML ahora usa un elemento DOM. Se conservó el copy; el contador `web_js_literal_ui_text` baja de 66 a 62 (tope versionado: 65) y `web_js_html_concat` de 226 a 224 (tope: 226). El asset compartido del cliente API se registra como dependencia de `AppAsset` antes de ambos widgets. La prueba focalizada de inicialización detectó que el widget de receta invocaba su IIFE sin pasar el objeto global; se corrigió la invocación y se verificó que ambos widgets representen los estados vacío y con botón.

El cliente API centraliza la resolución de rutas y URL externas para los widgets de descarga, conservando el resolver de la SPA. La operación común de descarga centraliza la política de cabeceras y MIME: solo adjunta cabeceras autenticadas cuando la URL resuelta es del mismo origen, y solo descarga respuestas PDF exitosas. Las URLs absolutas externas reciben cabeceras vacías para no exponer credenciales de Bioenlace a otro origen.

Para descargas del mismo origen, el cliente API obtiene el JWT de la sesión cuando todavía no hay uno y renueva/reintenta una sola vez ante un `401`, igual que las solicitudes JSON. No intenta renovar la sesión para URLs externas.

La descarga de blobs y la liberación de sus object URLs también están centralizadas en el cliente API; los widgets conservan sus nombres de archivo predeterminados y comparten el mismo ciclo de limpieza.

Ambos widgets de descarga son idempotentes al inicializarse sobre un mount existente: la salida vacía y el botón reemplazan el contenido anterior en lugar de acumular elementos. Se verificó la inicialización repetida en los dos estados.

Se eliminó un bloque comentado y sin consumidor que aún contenía la implementación HTML anterior del panel de última vacuna. No cambia el runtime y redujo el contador `web_js_html_concat` de 224 a 222.

Los widgets de preview de impacto de licencias y de configuración de agenda pasaron de construir markup concatenado a crear nodos DOM y asignar datos dinámicos mediante `textContent`. Se mantienen los mensajes, clases, fechas, límites de resultados, estados de carga/error y las modalidades de consulta automática o manual; los datos recibidos no se interpretan como markup. El hint de duración de licencia también monta su elemento con DOM en lugar de `insertAdjacentHTML`; conserva la actualización ante eventos `change` e `input`. En el renderizador UI JSON, los cargadores de contenido y los flujos de búsqueda de la SPA, las alertas de respuesta inválida, bloques no soportados, errores y estados de carga ahora usan nodos DOM con texto separado. Los errores incluyen URL y mensaje como texto, no como markup. En esa medición intermedia se registró `web_js_html_concat` 164/226, `web_js_literal_ui_text` 62/65 y `web_views_logic` 39/39; la métrica se redujo más en iteraciones posteriores.

Se refactorizó el autocomplete del wizard SPA: las filas de fechas/franjas, opciones y estados de carga/error se construyen con DOM; los valores de API se asignan como texto y atributos, sin concatenarlos en HTML. Se preservan la selección de fecha/franja, el formato de resultados y el ocultamiento del panel al seleccionar; una prueba runtime con DOM stub verificó cambio de fecha, selección y render seguro de un label con contenido tipo markup. Los widgets PDF de laboratorio y receta también reemplazan su mount al reinicializarse, evitando acumular mensajes vacíos; se verificaron ambas inicializaciones repetidas. Se reemplazaron además el estado vacío de atajos, el indicador de carga de tarjetas y el spinner de envío del formulario CRUD por DOM, preservando los nodos originales del botón tras concluir el envío. En UI JSON, los wrappers de bloques se construyen con DOM y se conservan en orden junto al banner de validación; los bloques de mensaje usan texto simple y preservan severidad y saltos de línea. Las vistas de lista en tabla, tarjetas y selección interactiva también generan estructura DOM. Una prueba runtime verificó que títulos, encabezados, datos directos, `meta.*`, nombres y subtítulos tipo markup se representen como texto, y que la selección múltiple habilite confirmación y mantenga los indicadores. Medición actual: `web_js_html_concat` 123/226, `web_js_literal_ui_text` 64/65 y `web_views_logic` 39/39.

El formulario UI JSON ahora también construye con DOM su estructura, campos ocultos, controles y botón de envío. Select, radio, chips, número, fecha, hora, display, texto, textarea, autocomplete y custom widgets conservan sus atributos, valores iniciales, hints y metadata; campos y opciones dinámicas se escriben como valores/texto. La conversión aplica a UI JSON, y deja intactos los renderizadores legacy del formulario CRUD fuera de ese flujo. Una prueba runtime del bloque completo verificó la estructura, tipos de control, valores, metadata y representación segura como texto.

En la carga AJAX del formulario de captura, los mensajes de condición ahora se envían como texto plano y se montan en alertas DOM, sin concatenarse con HTML. Se conserva la vista parcial renderizada por Yii como fragmento HTML independiente; una prueba runtime verificó que el mensaje con contenido tipo markup se represente como texto y que el formulario mantenga su estructura. Medición: `web_js_html_concat` 110/226, `web_js_literal_ui_text` 64/65 y `web_views_logic` 39/39.

El indicador reutilizado al cargar pasos del flow y definiciones UI ahora se monta con DOM. Conserva clases, atributos accesibles, spinner y mensaje por defecto, mientras muestra cualquier mensaje dinámico como texto; la prueba runtime focalizada pasó. Esta conversión no altera el contador de concatenación HTML porque ese helper ya asignaba una cadena a `innerHTML`, pero elimina la interpretación de su contenido como markup.

El resumen que reemplaza el flow al completar el envío también se monta con DOM: mantiene el encabezado/tone existente, los saltos entre líneas y la animación; los títulos y valores variables usan `textContent`/nodos de texto. El fallback «Listo.» se centralizó en `BioenlaceApiClient` para conservar el contador de textos UI en 64/65. La prueba runtime comprobó tono del encabezado y valores tipo markup representados literalmente en el resumen. Los dos errores de resolución de UI del flow también se construyen como alertas DOM; el identificador dinámico de acción se agrega como texto y los copy permanecen centralizados en `BioenlaceApiClient`. Se verificaron ambos mensajes y el caso de un identificador con apariencia de markup; los contadores se mantienen en `110/226`, `64/65` y `39/39`.

Los datos adicionales de persona (nombre y DNI) en respuestas del asistente ya no se concatenan a la explicación como HTML: se agregan en un bloque DOM separado con etiquetas y valores de texto, manteniendo el formato y separadores. La explicación original conserva su renderizado, y se verificó que datos con apariencia de markup aparezcan literalmente. Los contadores del auditor no cambian (`110/226`, `64/65`, `39/39`), ya que esa concatenación no estaba incluida en su patrón de medición.

Las tarjetas de acciones sugeridas del asistente ahora se construyen con DOM y se pasan al panel como `DocumentFragment`; se mantienen la grilla, encabezado, metadata de `client_open`, listeners, y textos/atributos dinámicos. El copy del encabezado se centralizó para conservar el límite de literales UI. La sugerencia interactiva en respuestas informativas también se monta con DOM y texto, manteniendo el listener que reenvía la consulta. Prueba runtime verificó la restauración del nodo y del listener tras repeticiones de carga. Auditoría actual: `web_js_html_concat` 94/226, `web_js_literal_ui_text` 64/65 y `web_views_logic` 39/39.

Los atajos de bienvenida y del toolbar ahora comparten construcción DOM para botones, títulos y grillas.
